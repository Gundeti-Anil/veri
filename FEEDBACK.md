# Feedback for World (World ID / IDKit)

Written during ETHGlobal ETHOnline 2026 while integrating World ID Orb ("proof of
human") verification into Veri's registration flow. Logged as we hit each issue,
not reconstructed afterward.

## Summary

We could not find any API path, for a hackathon/developer-tier World account,
that successfully verifies a Sandbox-simulated credential end-to-end. We are
shipping with the World API network call stubbed (`WORLD_STUB_VERIFY=true` in
`veri-agent-hub-main/backend/src/world.js`) — everything else in the flow
(RP-signed request, on-device proof generation, nullifier replay protection,
humanId derivation, EIP-712 attestation, on-chain registration) is fully real
and unaffected.

## What we confirmed, in order

1. **Selfie Check is access-gated Beta, undocumented in the client.** The World
   App's "Add credential" screen shows Face credential as "Coming soon" with no
   indication that it requires requesting Beta access
   (`developers@toolsforhumanity.com`) per-app. We only found this in
   `docs.world.org/world-id/idkit/credentials`, not surfaced anywhere in-app.
   Switched our integration to `orbLegacy()` / Orb verification instead, which
   is not gated.

2. **v4 verify API error messages don't match the actual required request
   shape**, and several were actively misleading:
   - Sending `verification_level` / `nullifier_hash` field names inside
     `responses[]` (the flattened field names IDKit's own result object uses)
     produces `"Unknown protocol_version"` — a completely unrelated error code
     that gave no hint the real problem was field naming.
   - The correct field names are `identifier` / `nullifier`, undocumented in
     any page we found; we only discovered them by omitting `protocol_version`
     entirely and reading the resulting error, which happened to reference the
     correct field names in its `detail` string.
   - `rp_context` as a nested object (which `signRequest()` from
     `@worldcoin/idkit-server` produces, and which IDKit's own client-side hook
     requires as input) is **not** what the verify endpoint wants — it wants a
     flat top-level `nonce` field instead. Nothing in the docs we read states
     this; we found it only by trial.
   - Valid `identifier` values are undocumented anywhere we could find; we only
     learned `orb` is correct (not `proof_of_human`, despite that being the
     preset function's name) from an error message's `detail` string.

3. **Two verify hosts, two different and incompatible failure modes, for
   identical requests:**
   - `staging-developer.worldcoin.org/api/v4/verify/{rp_id}` — always returns
     `{"code":"app_not_migrated","detail":"...use the v2 verify endpoint"}`,
     regardless of app config. Confirmed on two separate apps: one that
     inherited a half-finished signer/RP registration, and one created fresh
     from scratch specifically to rule out account-specific state. Both fail
     identically. This appears to be a platform-wide limitation of the staging
     verify host, not a per-app migration status.
   - `developer.world.org/api/v4/verify/{rp_id}` (production) — correctly
     processes the v4 request (gets to real proof validation), but rejects
     every proof generated by the Sandbox World App with
     `{"code":"invalid_merkle_root","detail":"...User appears to be
     unverified."}`, even immediately after completing a simulated Orb
     enrollment in-app via "Face embedded signup → Select an image."
   - The legacy v2 endpoint (`developer.worldcoin.org/api/v2/verify/{app_id}`)
     that the `app_not_migrated` error tells you to fall back to does not
     recognize actions created under the newer RP/World ID Configuration UI at
     all (`{"code":"invalid_action","detail":"Action not found."}`), even
     though that same action works fine for signing RP requests via v4.

   Net effect: a Sandbox-generated proof's Merkle root apparently lives in a
   tree that staging refuses to check (for our account tier) and production
   doesn't recognize. We could not find a combination of host + API version
   that both accepts the request format *and* recognizes a Sandbox identity.

4. **The RP/signer registration UI state doesn't reflect verify-API
   capability.** We initially found "Register relying party" unclicked with no
   signer address configured. Completing it (Configure signer key → Generate
   new key) did not change the `app_not_migrated` behavior on staging at all —
   suggesting that UI's "migrated" state and the verify API's internal
   migration flag are not the same thing, or that staging verify simply isn't
   available to this account tier regardless of per-app setup.

## What would have saved us significant time

- Document the exact required v4 `responses[]` field names (`identifier`,
  `nullifier`) and valid `identifier` enum values (`orb`, `secure_document`,
  `document`, `device`, `face`, `selfie`) directly on the verify API reference
  page — we only found them by reverse-engineering error messages.
- Document that `rp_context` should not be forwarded to the verify endpoint
  as-is, and that a flat `nonce` is expected instead.
- Either make the staging verify host actually work for Sandbox-tier accounts,
  or document clearly, in one place, which host/API-version combination is
  expected to validate a Sandbox-App-generated proof — and put that statement
  directly on the Sandbox testing guide, not scattered across separate pages.
- Surface Selfie Check's Beta/access-gating status in the World App's own "Add
  credential" screen (e.g. "Selfie Check — request access" instead of a bare
  "Coming soon"), since as external developers we had no visibility into
  whether it was a client bug, a rollout timing issue, or an access gate until
  we found one doc page that mentioned requesting access by email.

## What we did not have time to try

- Filing a support request with World and waiting for a response (out of
  scope for a hackathon timeline).
- Testing with a production/Business-tier World account, which may not hit
  this same account-tier gap.
